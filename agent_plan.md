## 2. Non-negotiable product laws

1. This is Joe's standalone platform, not Creator OS, a social network, a multi-creator system, or a ticket marketplace.
2. Do not invent Joe's biography, clients, logos, metrics, testimonials, pricing, contact details, event details, or claims. Use conspicuous non-production placeholders and surface an admin `content incomplete` warning.
3. Production content lives in the CMS or an approved import, never hardcoded in application components.
4. Use a modular monolith: Next.js 16 App Router frontend and Go 1.25+ REST API with explicit domain boundaries; do not introduce microservices in v1.
5. MongoDB uses the official Go driver. External identifiers are stable UUIDs; money is Decimal128 plus ISO currency, never binary floating point.
6. Every protected action is authorized server-side. Administrators require MFA. Sensitive actions and exports are audited.
7. Payment webhooks, not browser redirects, confirm payment. Inventory reservation, webhook handling, issuance, and check-in are atomic/idempotent and cannot oversell or admit twice.
8. Never expose personal data in QR payloads, logs, analytics, public URLs, or scanner responses. Store only secure hashes of bearer ticket tokens where possible.
9. Every vertical slice includes data/schema/index work, domain/service logic, authorization, UI, tests, telemetry, and documentation as applicable. UI-only work is not complete.
10. Public UI is mobile-first from 320px, WCAG 2.2 AA, localization-ready, SEO-complete, and targeted at mobile p75 LCP <= 2.5s.
11. Preserve staging/production isolation for MongoDB, Cloudinary folders, Resend recipients, secrets, and analytics projects.
12. No ticket becomes `DONE` without commands and/or manual evidence recorded in its row or the Verification Ledger.

## 3. Status vocabulary and claim protocol

Allowed states: `TODO`, `READY`, `IN PROGRESS`, `IN REVIEW`, `BLOCKED`, `DONE`.

Before editing code, every agent must:

1. Pull/reconcile the latest shared work and re-read this entire plan.
2. Select one `READY` ticket whose dependencies are `DONE`.
3. Check that its **exclusive paths** do not overlap another `IN PROGRESS` ticket.
4. Atomically change the ticket to `IN PROGRESS`, set `Owner` to a unique agent name, add `Claimed` timestamp, and update dashboard counts **before** editing implementation files.
5. Create a short handoff entry under Section 11 if the slice will span sessions.

While working:

- Edit only the ticket's exclusive paths. Shared files require the reservation rules below.
- Re-read this plan before migrations, API contracts, generated clients, root dependency files, or shared design primitives are changed.
- If scope expands, split a new ticket; do not silently absorb another lane.
- If blocked, record the concrete blocker and the exact unblocking action, release exclusive paths, and mark `BLOCKED`.

To close a ticket:

1. Run ticket tests plus all affected quality gates.
2. Record concise evidence (commands, result, commit/PR if applicable) in Section 10.
3. Change to `IN REVIEW`; another agent reviews behavior, security, tests, and path scope.
4. Reviewer records their name and evidence, then marks `DONE` and promotes newly unblocked tickets from `TODO` to `READY`.
